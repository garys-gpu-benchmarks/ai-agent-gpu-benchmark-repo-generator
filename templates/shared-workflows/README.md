# shared-workflows

[![Self-test](https://github.com/__CI_OWNER__/__CI_SHARED_REPO__/actions/workflows/self-test.yml/badge.svg)](https://github.com/__CI_OWNER__/__CI_SHARED_REPO__/actions/workflows/self-test.yml)

Reusable GitHub Actions workflows for the GPU benchmark suite: 128 workload
repositories ({AMD, NVIDIA} × {Ubuntu 24.04, 26.04} × 32 workloads) under
[`__CI_OWNER__`](https://github.com/__CI_OWNER__). The CI logic lives here
once. Each workload repository holds only two short caller files that pin a
release tag of this repository.

This repository is generated by `scripts/emit_shared_workflows.py` in the
benchmark repository generator, from `templates/shared-workflows/` and
`config/ci_contract.yaml`. Change it there, not here, so the callers and the
reusable workflows cannot drift apart.

## Workflows

| Workflow | Runs on | Trigger in the caller | What it does |
|---|---|---|---|
| [`ci.yml`](.github/workflows/ci.yml) | GitHub-hosted `__HOSTED_RUNNER__` | `pull_request`, `push` to `main` | shellcheck, ruff __RUFF_VERSION__, `bash -n` / `compileall` / `run_benchmark.sh --help`, specification schema and config parse, `validate_results.py --seed-fixture`, required-file check, actionlint __ACTIONLINT_VERSION__, and a job summary table. Never installs a GPU stack or runs the benchmark. |
| [`gpu-smoke.yml`](.github/workflows/gpu-smoke.yml) | self-hosted `[self-hosted, gpu, <vendor>, <os_label>]` | `workflow_dispatch` only | Verifies the pre-provisioned GPU stack (installs nothing), records `results/environment.json` (driver, ROCm/CUDA, kernel, GPU), runs `run_benchmark.sh --<profile>`, puts headline metrics in the job summary, and uploads the results. |
| [`self-test.yml`](.github/workflows/self-test.yml) | GitHub-hosted | push / pull request to this repository | Runs actionlint on these workflows and runs `ci.yml` against [`tests/fixtures/sample-workload`](tests/fixtures/sample-workload). |

### Inputs

| Input | Workflow | Required | Values |
|---|---|---|---|
| `vendor` | both | yes | `__VENDOR_CHOICES__` |
| `os_label` | both | yes | `__OS_LABEL_CHOICES__` |
| `profile` | `gpu-smoke.yml` | no (default `__PROFILE_DEFAULT__`) | `__PROFILE_CHOICES__` |
| `python_version` | `ci.yml` | no (default `__PYTHON_VERSION__`) | any `actions/setup-python` version |
| `working_directory` | `ci.yml` | no (default `.`) | workload root inside the checkout; used by the self-test |

Both workflows reject any `vendor`, `os_label` or `profile` value outside these lists.

### Example caller

What the generator writes into every workload repository (repository 101 shown):

```yaml
# .github/workflows/ci.yml
name: CI
on:
  pull_request:
    branches: [main, develop]
  push:
    branches: [main]
permissions:
  contents: read
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true
jobs:
  ci:
    uses: __CI_OWNER__/__CI_SHARED_REPO__/.github/workflows/ci.yml@__CI_REF__
    with:
      vendor: amd
      os_label: ubu2404
```

The GPU caller is the same shape with `on: workflow_dispatch` (plus a
`profile` choice) and `uses: …/gpu-smoke.yml@__CI_REF__`.

## Why GPU runs never start from a pull request

The GPU job runs on self-hosted machines. If a `pull_request` trigger could
reach it, anyone who forks a public workload repository could open a pull
request and run arbitrary code on that hardware. The callers therefore start
`gpu-smoke.yml` only through **Run workflow** (`workflow_dispatch`), which
requires write access to the repository. The generator's self-check fails a
workload whose GPU caller lists `pull_request`.

Hosted checks and GPU runs are separate for a second reason: the hosted job is
free, fast and runs on every change, while a GPU run is expensive and its
numbers are only meaningful on a known, quiet machine.

## Self-hosted GPU runners

`gpu-smoke.yml` expects runners that are:

1. **Registered at the organization level** (Organization → Settings → Actions →
   Runners → New runner), so every workload repository can use them. A runner
   registered to one repository serves only that repository.
2. **Labeled** `gpu`, the vendor (`amd` or `nvidia`) and the OS (`ubu2404` or
   `ubu2604`), for example `--labels gpu,amd,ubu2404`. The job asks for all four
   labels (`self-hosted` is added automatically), so an AMD 24.04 benchmark can
   only land on an AMD 24.04 machine. The job also checks `/etc/os-release`
   against `os_label`.
3. **Pre-provisioned**: GPU driver and ROCm or CUDA already installed. The
   workflow verifies them (`rocminfo` / `nvidia-smi`) and fails clearly if they
   are missing; it never installs a host GPU stack. Each workload's
   repository-local `.venv` is built on that workload's first run by
   `run_benchmark.sh` → `scripts/ensure_setup.sh`, and reused afterwards
   (`actions/checkout` runs with `clean: false`). The runner user needs
   passwordless `sudo` for that first `setup.sh` run.
4. **One runner agent per GPU host.** A runner agent runs one job at a time, so
   this is what keeps two benchmarks from sharing a GPU and skewing each
   other's numbers. (A `concurrency` group in the caller only prevents two runs
   of the *same* repository; it cannot coordinate across repositories.)

## Versioning and releases

Callers pin a floating major tag, `@__CI_REF__`.

| Change here | Example | What you do | Effect on workload repos |
|---|---|---|---|
| Compatible | add a check, fix a bug, bump an action | tag an exact release (`v1.2.0`) and move `v1` to it | picked up on their next run, no edits |
| Breaking | rename or remove an input, add a required input | tag `v2.0.0` and `v2`; leave `v1` where it is | none until the generator's `ci_contract.yaml` says `ref: v2` and the workloads are regenerated |

Exact tags (`v1.2.0`) never move. Major tags (`v1`) float to the newest
compatible release. This is the same convention GitHub's own actions use.

### Releasing a change

```bash
# publish_benchmarks_to_github.sh does steps 1-3a for you. By hand:
# 1. Regenerate from the generator (writes this folder; keeps .git).
#    <publish folder> holds shared-workflows/, e.g. Publishing/Publish_20261009_01
python3 scripts/emit_shared_workflows.py --output-root <publish folder> --update

# 2. Commit, push, and wait for the Self-test workflow to pass
git add -A && git commit -m "ci: <what changed>" && git push

# 3a. Compatible change: release it and move the major tag
git tag v1.2.0 && git push origin v1.2.0
git tag -f v1 v1.2.0 && git push -f origin v1

# 3b. Breaking change: start a new major line instead
git tag v2.0.0 && git tag v2 v2.0.0 && git push origin v2.0.0 v2
```

Moving `v1` affects every workload repository at once, which is why the
Self-test must pass first. Record each release in [`CHANGELOG.md`](CHANGELOG.md).

## Keeping actions current

[`.github/dependabot.yml`](.github/dependabot.yml) checks the `actions/*`
versions weekly and opens one grouped pull request when they change. The
Self-test runs on that pull request; merge it, then release as above.
